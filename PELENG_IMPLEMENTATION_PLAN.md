# План реализации «Пеленг» в TrackStudio

Статус: план согласован по инженерному подходу; официальные критерии конкурса ещё нужно сверить с организаторским сайтом/материалами. Этот документ не утверждает, что все этапы уже реализованы.

## Принципы

1. Двигаться по одному этапу. Этап считается закрытым только после выполнения его критериев и фиксации результата.
2. Не ломать существующий сценарий TrackStudio с RTSP-камерами и BEV-merger.
3. Разделять источник видео, калибровку камеры, детекцию/трекер, 3D-геометрию и визуализацию. Тогда способ проверки меняется настройкой, а не переписыванием алгоритма.
4. Не путать координаты BEV (вид сверху) с метрическими координатами X/Y/Z в общей мировой системе.
5. Всегда отмечать, что реально проверено автоматически, что проверено вручную и что ещё не проверено на физических камерах.
6. Не обещать точность без теста с известной геометрией/ground truth.

## Два взаимозаменяемых режима проверки

Предлагаемая единая настройка источников, с возможностью выбрать режим конфигурацией:

- **Файлы видео** — один файл на камеру, параметры времени начала/смещения, FPS/таймстемпы. Удобно для воспроизводимых тестов и регрессий.
- **Живые камеры** — RTSP/RTMP-потоки телефонов через существующий MediaMTX/совместимый источник. Сначала проверяем доступность и синхронизацию потоков, затем 3D.
- Оба режима должны отдавать кадры через общий интерфейс источника. Триангуляция не должна знать, пришёл кадр из файла или из телефона.
- Для первого MVP можно использовать существующий путь видео → FFmpeg/MediaMTX → RTSP, если это позволит не менять runtime раньше времени. Нативную загрузку/чтение файлов добавлять как отдельный адаптер после проверки текущего API. Выбор фиксируется после аудита точек входа приложения.

Предлагаемая конфигурация (эскиз, не реализованная схема API):

```yaml
input:
  mode: video  # video | live
  cameras:
    - id: cam0
      source: ./data/cam0.mp4
      time_offset_ms: 0
    - id: cam1
      source: ./data/cam1.mp4
      time_offset_ms: 0

calibration:
  file: ./data/calibration.json
  world_unit: meter

tracking:
  detector: existing
  merger: existing

output:
  show_2d: true
  show_3d: true
  save_trajectory: true
```

Это только целевой пример. Реальные названия полей должны соответствовать существующей конфигурации TrackStudio и не должны внедряться до аудита её схемы.

## Этапы и критерии завершения

### Этап 0 — требования и базовая воспроизводимость (текущий этап)
- Зафиксировать официальные требования, формат демонстрации и критерии оценки, когда они доступны.
- Сохранить исходный способ запуска TrackStudio.
- Проверить текущую конфигурацию, зависимости, тесты и CI.
- Составить таблицу «требование → модуль → команда проверки → критерий успеха».
- Не начинать следующую функциональную интеграцию, пока команда запуска и базовые проверки не задокументированы.

**Готово, когда:** есть проверенная инструкция запуска, известны существующие входные/выходные интерфейсы и список неизвестных требований. В данный момент новый 3D-код ещё не подтверждён запуском тестов.

### Этап 1 — проверка геометрии независимо от видео
- Запустить синтетические тесты `tests/test_triangulation_3d.py`.
- Проверить lint/type checks по настройкам репозитория.
- Исправить ошибки до интеграции.
- Добавить тесты на единицы измерения, плохую геометрию камер, reprojection threshold и недостаточную базу камер, если аудит покажет пробелы.

**Готово, когда:** тесты проходят локально и/или в CI с сохранённым логом; результат и ограничения записаны.

### Этап 2 — формат калибровки и единая мировая система
- Сопоставить существующий `CameraCalibration` и текущий файл калибровки с новым `CameraModel`.
- Явно задокументировать оси мира, handedness, единицы, внутренние параметры K, дисторсию, R/t и способ получения калибровки.
- Не подменять метрическую калибровку одной BEV-гомографией.
- Добавить валидацию и понятные сообщения об отсутствующей/невалидной калибровке.

**Готово, когда:** калибровка конвертируется однозначно, а тестовая 3D-точка проецируется и восстанавливается в согласованных единицах.

### Этап 3 — адаптеры источников и синхронизация
- Описать единый интерфейс кадра: camera_id, frame, timestamp, frame_id/source metadata.
- Реализовать/подтвердить два переключаемых режима: файлы и живые потоки.
- Для видео обеспечить повторяемое воспроизведение, контроль FPS и временных смещений.
- Для live — диагностировать задержку, пропуски кадров и рассинхронизацию.
- UI/API не должны требовать переписывания 3D-ядра при смене режима.

**Готово, когда:** один и тот же pipeline запускается на тестовых файлах и на доступных live-потоках через переключение конфигурации.

### Этап 4 — интеграция детекций и 3D-точек
- Определить точку наблюдения объекта (например, центр нижней границы bbox для объектов на земле; правило должно соответствовать целевому объекту).
- Сопоставлять наблюдения одного объекта между камерами с учётом времени, класса, геометрии и reprojection error.
- Триангулировать только согласованные наблюдения, сохранять качество и причину отказа.
- Не считать одинаковые локальные track_id разных камер одним global_id без отдельного cross-camera association.

**Готово, когда:** на воспроизводимом многокамерном примере выводятся мировые X/Y/Z, camera IDs, timestamp, reprojection error и статус качества.

### Этап 5 — траектории и стабильность
- Поддержать постоянный global_id между кадрами и камерами.
- Фильтровать шум (например, Kalman/robust smoothing) только после оценки сырых измерений.
- Обрабатывать пропуски, потерю камеры, выбросы и повторное появление объекта.
- Экспортировать траектории в CSV/JSON с единицами и временными метками.

**Готово, когда:** тест движения объекта создаёт связную траекторию без немотивированных скачков и с понятной обработкой пропусков.

### Этап 6 — интерфейс и удобство демо
- Показывать состояние каждого источника, число детекций/треков, 3D-позиции, траектории, reprojection error и предупреждения о калибровке/синхронизации.
- Переключение `video` / `live` через конфиг и, если архитектура приложения позволяет безопасно, через UI.
- Сохранить минимальный сценарий запуска одной командой и пример конфигурации.
- Ошибки должны говорить, что сделать дальше, а не только печатать stack trace.

**Готово, когда:** человек, не знакомый с кодом, может выбрать режим, запустить демо и увидеть результат по README.

### Этап 7 — валидация и демонстрация
- Сначала синтетический ground truth с известными координатами.
- Затем видео, где геометрия/разметка известна настолько, чтобы посчитать ошибку.
- Затем реальные телефоны: фиксированное расположение, измеренные расстояния между камерами и контрольные точки в сцене.
- Отдельно измерить 3D MAE/RMSE/P95, reprojection error, долю успешных реконструкций, ID switches и end-to-end latency/FPS.
- Записать версии зависимостей, конфиг, команды и результаты; не публиковать цифры без повторяемого протокола.

**Готово, когда:** есть воспроизводимый отчёт и короткий сценарий демонстрации; известны ограничения и условия, при которых система работает.

## Команды проверки (уточняются после проверки окружения)

Из корня клона репозитория:

```bash
uv sync --dev
uv run pytest tests/test_triangulation_3d.py -q
uv run ruff check trackstudio/geometry tests/test_triangulation_3d.py
uv run trackstudio run -c test_config.json --vision-fps 10
```

Последняя команда требует запущенного MediaMTX и доступных источников из `test_config.json`; это smoke test приложения, а не доказательство точности 3D. Если в репозитории нет `uv`, можно использовать установленный Python/venv и команды `pytest`, `ruff`, `trackstudio` после установки dev-зависимостей.

## Неизвестные вопросы, которые нельзя молча выдумывать

- Точные критерии и формат сдачи «Пеленга».
- Какой объект и какая точка объекта должны иметь координаты XYZ.
- Требуется ли метрическая точность и есть ли допустимая погрешность.
- Есть ли готовые параметры калибровки или их нужно получать на месте.
- Сколько камер минимум, какой способ синхронизации допустим.
- Должен ли пользователь загружать файлы через UI или достаточно положить их в папку и указать в конфиге.
- Какие ОС/GPU/сетевые ограничения есть на площадке.

Если на какой-то вопрос пока нет ответа, выбирается обратимое значение по умолчанию и оно явно документируется.
